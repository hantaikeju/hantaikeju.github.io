## 概述

学完了线程、消息传递、共享状态、以及异步编程的各个层面，本篇从**全局视角**将它们串联起来——理解 Future、任务、线程三者各自的角色，以及如何根据实际场景做出选择。

---

## 三个层级：Future → Task → Thread

Rust 的并发体系可以理解为三个边界清晰的层级：

```
┌─────────────────────────────────────────────┐
│  线程 (Thread)                               │
│  ┌───────────────────────────────────────┐  │
│  │  任务 (Task)                           │  │
│  │  ┌─────────────────────────────────┐  │  │
│  │  │  Future 树                       │  │  │
│  │  │  ┌─────┐  ┌─────┐  ┌─────┐    │  │  │
│  │  │  │ Fut │  │ Fut │  │ Fut │    │  │  │
│  │  │  └──┬──┘  └─────┘  └─────┘    │  │  │
│  │  │  ┌──┴──┐                       │  │  │
│  │  │  │ Fut │                       │  │  │
│  │  │  └─────┘                       │  │  │
│  │  └─────────────────────────────────┘  │  │
│  └───────────────────────────────────────┘  │
│  操作系统管理                                │
└─────────────────────────────────────────────┘
```

| 层级 | 管理者 | 边界 | 特点 |
|------|--------|------|------|
| **Future** | 任务（Task） | 异步操作最小单位 | 可组成树形结构，可被取消 |
| **Task** | 异步运行时（Executor） | 异步操作的集合边界 | 任务内和任务间都可并发 |
| **Thread** | 操作系统 | 同步操作的集合边界 | 线程间可并发运行 |

> 运行时（确切地说是其 executor）负责管理**任务**，任务则负责管理**futures**。任务就像是运行时管理的**轻量线程**。

---

## 线程与异步的关键差异

| 特性 | 线程 | 异步任务 |
|------|------|----------|
| **启动模型** | 一次性启动就运行到底 | Future 惰性执行，需 `.await` |
| **内部并发** | 无原生机制 | 任务内可在多个 Future 间切换 |
| **中断机制** | 无取消机制（除非 OS 打断） | Future 结束时状态被正确清理，天然支持取消 |
| **调度** | 操作系统抢占式 | 运行时协作式（`.await` 点让出） |
| **开销** | 较高（OS 线程栈） | 较低（用户态任务） |

> 线程有点像"一次性启动就运行到底"，没有中断点——除非被操作系统抢占。

---

## 线程 + 异步：协同工作

在实践中，选择往往不是"线程或异步"，而是**"线程加异步"**：

- 异步模型提供了一种**不同但互补**的权衡方式
- 并发操作不需要各自的线程——它们可以在**任务**上运行
- 任务类似于线程，但由**运行时**而非操作系统管理

### 两种构建 Stream 的方式

| 方式 | 适用场景 |
|------|----------|
| **用异步任务构建 Stream** | IO 密集型、事件驱动 |
| **用线程构建 Stream** | CPU 密集型、需要 OS 级隔离 |

### 工作窃取（Work Stealing）

许多异步运行时（包括 trpl 使用的运行时）默认是**多线程**的，并使用**工作窃取**机制：

```
线程 1: [Task A] [Task C] ──────→ 空闲，偷 Task B ──→ [Task A] [Task C] [Task B]
线程 2: [Task B] [Task D] [Task E] ──→ [Task D] [Task E]
```

- 任务可以在不同线程之间**透明地移动**
- 根据线程利用率**优化整体性能**
- 这种机制需要**线程、任务和 Future 三者的配合**

`spawn_blocking` 和 `spawn_task` 正是这种协同的体现——前者将阻塞操作放到专用线程池，后者在异步运行时中调度轻量任务。

## 默认参考：如何选择

### 优先用线程

- 任务可以**高度并行**——比如处理一批可以分开处理的数据（数据并行）
- CPU 密集型计算
- 需要 OS 级别的隔离和抢占

### 优先用 async

- 任务**高度并发**——比如处理来自多个不同来源、间隔不一的网络请求
- IO 密集型场景
- 需要任务内细粒度的切换和取消能力

### 两者结合

既需要并行又需要并发时，不必非选其一——可以自由地结合起来：

```
spawn_blocking(|| {
    // CPU 密集型：在专用线程池中运行
    heavy_computation()
});

spawn_task(async {
    // IO 密集型：在异步运行时中运行
    fetch_data().await;
});
```

## 小结

| 概念 | 一句话 |
|------|--------|
| **Future** | 异步计算最小单位，可组成树，惰性执行 |
| **Task** | 运行时管理的轻量线程，包含一组 Future |
| **Thread** | OS 管理的执行单元，同步操作边界 |
| **选择原则** | 并行多用线程，并发多用 async，需要两者就结合 |
| **工作窃取** | 运行时透明地在多线程间移动任务以优化性能 |

> 在 Rust 中，并发不仅仅是使用线程或 async 的问题——而是理解三者的层级关系，在不同层次选择合适的工具，并在需要时让它们协同工作。
